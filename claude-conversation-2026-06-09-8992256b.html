Step 4 – Retry a failed payment: mutation { retryPaypalSubscriptionPayment(subscriptionId: "I-XXXXXXXX", amount: "9.99", currencyCode: "USD") } can you elaborate what this is for?
🤖 Claude
When a scheduled billing cycle fails (e.g. the customer's card is declined or has insufficient funds), PayPal marks the subscription with an **outstanding balance**. The subscription stays active but that cycle's payment is unpaid. `retryPaypalSubscriptionPayment` calls PayPal's [Capture authorized payment on subscription](https://developer.paypal.com/docs/api/subscriptions/v1/#subscriptions_capture) endpoint (`POST /v1/billing/subscriptions/{id}/capture`) to manually collect that outstanding balance — it's the merchant saying "try charging this subscriber again right now." ### When you'd use it: 1. PayPal auto-charges the customer on their billing cycle → card declined 2. PayPal retries automatically up to the plan's `paymentFailureThreshold` (we set it to 3 in `createBillingPlan`) 3. All automatic retries fail → the subscription gets suspended or the cycle remains unpaid 4. Customer updates their payment method and tells support "please try again" 5. Merchant runs `retryPaypalSubscriptionPayment` to immediately capture the outstanding amount rather than waiting for the next scheduled retry ### The `amount` and `currencyCode` args: PayPal requires you to specify the amount explicitly for a manual capture — it's typically the same as the subscription cycle price, but could be a different value if the merchant negotiated a partial collection. `currencyCode` must match the subscription's currency (e.g. `"USD"`). In practice for most merchants the call is straightforward: ```graphql mutation { retryPaypalSubscriptionPayment( subscriptionId: "I-XXXXXXXX" amount: "9.99" currencyCode: "USD" note: "Customer updated payment method — retrying May cycle" ) } ```

The API call still works, but the sandbox buyer interface doesn't show the tracking panel. Here's how to confirm the tracking was actually pushed successfully: ### 1 — Check server logs When the fulfillment transitions to `Shipped`, you should see these log lines in your dev server output: ``` [PaypalPlugin] [verbose] Pushing shipment tracking to PayPal for order <code> — paypalOrder=..., capture=..., carrier=UPS, tracking=1Z999AA... [PaypalPlugin] [verbose] Shipment tracking pushed to PayPal for order <code>. ``` If you see an `[error]` line instead, it means the API call failed and will tell you why. --- ### 2 — Verify via the PayPal Orders API (Admin API query) You can confirm the tracking was recorded by fetching the PayPal order and checking its purchase unit: ```graphql # This isn't exposed as a query yet, but you can test it directly in Postman. # GET https://api-m.sandbox.paypal.com/v2/checkout/orders/<paypalOrderId> # Authorization: Bearer <access-token> ``` The response will include a `trackers` array under the purchase unit if tracking was successfully attached: ```json { "purchase_units": [{ "payments": { "captures": [{ "id": "...", "status": "COMPLETED" }] } }], "trackers": [{ "id": "<captureId>-<trackingNumber>", "status": "SHIPPED", "tracking_number": "1Z999AA10123456784", "carrier": "UPS" }] } ``` --- ### 3 — Check the Merchant dashboard instead of Buyer In the PayPal Sandbox **merchant** account ([sandbox.paypal.com](https://sandbox.paypal.com)): 1. Go to Activity → All Transactions 2. Find the relevant transaction 3. Click into the transaction details 4. Tracking appears under the merchant view, not the buyer view, in sandbox --- The production buyer experience (email notification + tracking panel in PayPal account) is only fully rendered in live PayPal accounts, not sandbox. The API behavior — recording the tracking against the capture — is identical between environments.
